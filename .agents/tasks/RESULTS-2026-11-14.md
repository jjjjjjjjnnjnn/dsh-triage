## TSK-20261112-009 · app-boot 启动诊断顺序与「二分排查」

**packet 的断言**：0.2.1-rc.5 的 app-boot 每条失败先输出自己的 id、阶段与所缺服务
（`packages/boot/app-boot/src/index.ts:1128`、`:1144`），汇总在 `:1118`（warning）与 `:1135`（startup failed）；
建议把 `dsh.profile.bundles` 削减到只剩 base，再逐个加回做二分定位。

**复核（实测，不是转述）**：本机 `app.asar` 里的 `@deepseek-ai/dsh-app-boot` 逐行读过，行号与语义**都对得上**，
但**包名与路径已经变了**：

| packet 的说法 | 本机实测 |
|---|---|
| `packages/boot/app-boot/src/index.ts` | `dsh/node_modules/@deepseek-ai/dsh-app-boot/src/index.ts`（1287 行） |
| `:1128` 每条失败输出自己的 id/阶段 | `inactiveDiagnostic()` 返回 `"<id> (<package>): <phase>: <error>"` |
| `:1144` 带完整失败详情 | `failureDetail(outcome)` 逐行缩进写出原始错误（栈可关） |
| `:1118` 可选插件的 warning | `activationDiagnostic()` → `"<bin>: warning: N entries did not activate"` |
| `:1135` 必需的 startup failed | `startupDiagnostic()` → `"<bin>: startup failed: N required plugins did not activate"`，随后分 `Failed plugins:` 与 `Plugins waiting for services (` 两段 |

**结论**：这条诊断逻辑是真的，但**它属于上游**。`dsh-triage` 能做的只有两件已经在做的事：
`probe` 把启动器自己的句子原样引用（`probe.startup-failed` 的 `detail` 就是 `first_line`），
以及 `host.ts:557` 见到 `startup failed` 就提前收工（不再空等两分钟）。**新增「二分排查」是一块新功能**，
在 `docs/BACKLOG.md` 里早已挂号：**`T-114 triage bisect`**（M3、implementer、依赖 T-301、"需要稳定启停一次 boot"），
状态 ⬜、尚未领取。本仓库不做功能轮，所以本轮**不实现**，只把 packet 的结论落到这里，
让下一个领 `T-114` 的人不必再去读上游源码。

**没有做的事**：没有新增命令、没有改判据、没有碰 `packages/`。packet 的验收命令在本轮结束时是绿的

## TSK-20261112-013 · `render controls (ubuntu, real browser)` 失败

**packet 的断言**：`verify` 在 `0b1bf5c` 上失败，四个 job 里只有 `render controls (ubuntu, real browser)` 红；
并让核对 `scripts/gate_render.mjs` 与 `browser_stderr`。

**复核（GitHub API 实读，不是转述）**：

1. packet 的**第一个断言已经过期**：run `43013253590`（`0b1bf5c`，2026-11-11T11:35:49Z）的四个 job 里
   `verify (node 24)` / `verify (node 22)` / `verify (windows, node 24)` / `gates can fail` **全绿**，
   只有 `render controls` 红 —— 与 packet 说的一致；但同一提交后来**重跑即绿**，所以它不是"必红"。
2. packet 让核对的 `scripts/gate_render.mjs` **在仓里不存在**（`Get-ChildItem scripts -Filter gate_render*` 空）。
   真正的入口是 `.github/workflows/ci.yml` 的 `render-control:` job，三步各跑一次
   `node scripts/record_render_fixture.mjs --mode blank|rendered|error`。
3. **失败形状与 R90 记过的同一个**：`43` 号 run 的失败行是
   `expectation not met: expected blank, got inconclusive` / `render said: inconclusive — document still loading · 14364ms` /
   `signals: root · children 0 · text 0 · html 204B · ready loading`。
   即页面已经 served、`#root` 在、但**文档始终停在 `readyState=loading`**，14.3s 用满预算 —— 不是白屏检测错了。
4. **`browser_stderr` 已经存在并且是这次派发的依据之一**：产物里 4001 字符，内容全是 GH runner 的
   `dbus/bus.cc:405 Failed to connect to the bus` 噪声，`browser_exit: null`，并且有
   `DevTools listening on ws://127.0.0.1:35129/…` —— **调试端口开了**，与 R90 那两次「端口从未出现」是**不同**的失败面。
5. **0.3.9 的发布提交（`3794ec3`，run `43315617523`）是另一件事**：红的是 `verify (node 24)` 的四条**本机读数**
   （`N6: CLI 与设置页在 collisions 上一致`、`M14-N1/N4`、`M15-N8`、`M15`），而 `render controls` 因为 `needs: verify`
   直接 **skipped**。R106 已经记录过这个形状（在干净 runner 上读本机 `~/.dsh`）。

**结论**：这份 packet 说的现象是真的，但**归因指向的脚本不存在**，而真正的下一步是 R90 已经选定、
HUMAN 尚未点头的那条路 —— 只改**启动参数**（`--disable-dev-shm-usage`，GH runner 的 `/dev/shm` 只有 64MB），
或只在「端口未开」这一种 detail 上做一次有预算的重试。本轮证据给出的新事实是：
**这次红不是端口问题，而是 `readyState=loading`**，所以「只在端口未开时重试」那条**覆盖不到它**。

**没有做的事**：没有改 `packages/probe/src/render.ts`（那要动产品代码与判定，属判据轮，需 HUMAN 点头）；
没有把 `expect blank` 放宽成「没观察到也算 blank」（R86 的红线）。`T-860` 在 `docs/BACKLOG.md` 里保持 🟨 进行中。
