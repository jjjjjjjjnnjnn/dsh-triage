> **日期**：2026-11-02｜**轮型**：判据修复（只动**检查器**与三条纯函数，**不动** `admission.ts` / 四桶 / `improved` 五门槛 / `data/gold/` / 20s / settle / readiness / 9 门 / D5 三个阈值）

## 1. 独立审核的结果：一半干净，一半不干净

| 角色 | 结论 |
|---|---|
| **verifier**（独立复算产物） | **零不一致**：R65 八条台账的 sha256 与文件逐字节相符（用 Node 与 `certutil` 两套实现双算）、`publish` 18 项 0 失败、`usability` 6/6、两个 listing 的 `checks[].id` 集合与 `inputs.tests` 一致。**唯一观察**：S8 相对 S5 只差 `generated_at`（说明「改完文档再跑」这次没有带来新读数——如实记录，不粉饰） |
| **adversary**（试图骗过新检查） | **找到 12 个缺陷，3 个高**。其中**三个高全部命中 R64/R65 刚写的规则本体**，且不需要恶意输入——一个自然写法、一个笔误就够 |

**这就是为什么自审不算数**：R65 我自己审出来的只有「`+01:00` 被拒」一条，而 adversary 一小时内拿出三条高的。

## 2. 三个高（都已修）

### 2.1 不存在的日期被放行，零信号

`judgePosting({postedOn:'2026-02-30T12:00:00Z'})` → **`ok: true, problems: []`**。

原因：`ISO_INSTANT` 只数位数（day `01–31` 全过），而 `Date.parse('2026-02-30')` 按 ES 规范**滚到 03-02**，于是「不在未来」也成立。一个字符的笔误（`12-02` → `02-30`）就通过了唯一一条与 D5 窗口有关的校验。

**这与该文件注释里自称已经修好的失败完全同形**——修的是拼写（`Z` 还是 `+01:00`），不是判据（「这个字符串是不是一个真实存在的时刻」）。

### 2.2 `NaN` 被写成了「不在未来」

`2026-13-01` / `99:99:99` / `+99:00` / `:60`（闰秒）→ **全部 `ok: true`**。

原因：`Number.isNaN(nowMs)` 检查的是 **`now`**，不是 `postedOn`；而 `NaN > nowMs` 为 `false`，`else if` 整条跳过。本仓的核心方法论是「读不到 ≠ 通过」，这里是唯一一处把「读不出」直接翻译成「通过」的代码，一行 `else if`。

### 2.3 一个 channel 说两个平台时，结论由数组下标决定

`POSTING_PLATFORMS.find(...)` 是首匹配，而 `discussion` / `issue` 排在 `x` 前面：

| 构造 | 修前行为 | 事实 |
|---|---|---|
| `channel:'Discussion on X'` + 真实 X URL | **拒**，理由是「不是 github-discussion URL」 | 事实正确却被拒，且理由指向一个通道没主张的平台 |
| `channel:'Discussion on X'` + GitHub discussion URL | **放行** | 通道说 X、URL 在 GitHub，账本自相矛盾却报绿 |

两个方向都不需要对抗性输入，「Discussion on X」是自然写法。

## 3. 修法（三条纯函数 + 一处调用方）

| 修法 | 位置 | 验收 |
|---|---|---|
| **`parseInstant()` 往返校验**：把字段拼成 epoch 再读回来，**民用字段必须原样存活**（`2026-02-30`→03-02 不符 → 拒；`月=13`/`时=99`/`:60` → 不符 → 拒；`±99:00` 先按「不是时区」拒；年份 <1000 拒） | `scripts/lib/posting.mjs` | 8 种不存在的时刻各自拒 + 3 种真实偏移量归一化到同一 epoch（单测） |
| **平台必须恰好一个**：`filter` 出所有被点名的平台；0 个 → 红；>1 个 → 红并列出被点名的集合（「一个条目 = 一次发布 = 一个 URL」） | 同上 | 三种双语 channel 双方向全拒（单测） |
| **日期校验挪到真正消费它的地方**：`record_d5_evidence.mjs` 在抓任何数据**之前**用 `parseInstant` 验 `--posted-on`，坏值 → **exit 2 零产物** | `scripts/record_d5_evidence.mjs` | 真跑 `--posted-on 2026-02-30T12:00:00Z` → exit 2、目录为空（实测） |

**第 3 条是这轮最值得记的**：adversary 指出「仓内唯一的瞬时校验被绑在 `registry.posted_on` 上，而那个字段**没有任何测量在读**；真正驱动 D5 的 `--posted-on` 零校验」。后果实测：`2026-02-30` 会让 `judgeD5` 从 `pending` 变 **`fail`**，`2026-13-01` 会让它变 **`no-post`**（「有帖子」被读成「没发帖」）。**校验必须在数据流上，而不是在文档里。**

## 4. 中危/低危也修了（都是「看起来更严格其实更松」那一类）

- **`judgeDistTags`**：`PUBLISHED_PACKAGES` 被 export 却从不参与判据 → 传一个**别的包**也叫「四个包一致」（`all 1 package(s) point latest at …` 绿）。现在缺包 = 点名 unmeasured + 红；同名出现两次、无名条目、空 `expectedVersion`、以及 `versions: null`（以前**跳过** dangling 检查并把 `next=9.9.9` 印在绿色 detail 里）现在都判红。
- **`judgeNextChange`**：`'0.2.1-rc.5 '`（尾空格）被读成「上游发新版」，并会打印 `upgrade --to " "`；`previous.version = ''` 被读成 `changed` 而不是 `baseline`。现在版本先 trim + 只接受可打印非空白（`^[!-~]+$`），坏基线 → `unmeasured`（不是「第一次观察」）。
- **`check_listing`**：`registry.json` 里一个 `null` 条目会让脚本 **TypeError 崩溃**，15 条断言一条都不产出（「检查没跑成」这种事本仓最忌讳）。现在如实报「条目不是对象」并继续；`status:draft` + `posted_url: ""` 不再被误报成「URL 已设置」。

## 5. 六条控制（全部真跑，全部保留产物）

| 产物 | 构造 | 期望 | 实得 |
|---|---|---|---|
| `listing-…T19-20-00` | `posted_on = +01:00` | 绿（R64 的修复不能被推翻） | exit 0 · 15/15 |
| `…T19-25-00` | 裸日期 | 红 | `is not an instant that exists … use Z or ±hh:mm` |
| `…T19-30-00` | 未来 | 红 | `posted_on is in the future` |
| `…T19-35-00` | 域不符 | 红 | `posted_url is not a github-discussion URL` |
| `…T19-40-00` | **`2026-02-30`**（adversary 的发现） | 红 | `is not an instant that exists` ← 修前是绿 |
| `…T19-45-00` | **双语 channel 双平台**（adversary 的发现） | 红 | `names more than one platform (github-discussion, x)` ← 修前是「按数组顺序」 |

每次改完立刻写回原串并复算 sha256；六次全部 `restored=true`。

## 8. R66 续：把修完的代码交回给同一个 adversary

修完之后我把同一批构造**送回去**让那个独立 adversary 重放——这是本仓第一次做「审 → 修 → 再审」的闭环。

**它的判定**：

| 高 | 判定 |
|---|---|
| 不存在的日期 | **真修好**：扫 **17,920** 个组合（5 年 × 月 00–13 × 8 个日 × 4 个时刻 × 8 个偏移），`parseInstant` 接受的 **7,824** 个值与 `Date.parse` **零分歧**（0 个 NaN、0 个不同时刻）。滚动被往返校验堵死在结构上 |
| `NaN` 当「不在未来」 | **真修好**：闸门挪到未来检查之前，偏移先做 `>23`/`>59` 范围检查，`now` 改用 `Number.isFinite`；它没找到能让 epoch 非有限的输入 |
| 双语通道歧义 | **假绿关闭，但第一版修法引入了新的误拒**：`X thread, not an issue`、`GitHub Discussions（不是 issue）` 这类「为排除而提到另一个平台」的写法被判歧义 |

**它还抓到三处第一版修法引入的问题**（都已修）：

1. **`drafts:[{}]` / `[[]]` 仍打死整轮**：我的守卫是 `typeof entry !== 'object'`，而数组和空对象都是 object；`file` 为空串时 `${DRAFTS_DIR}/` 就是目录，`readFileSync(目录)` 抛 **EISDIR**，15 条断言一条不产出。现在守卫要求「有非空 `file` 字符串」，坏行只是红一条断言。
2. **（同上第 3 行的误拒）**：判据从「channel 里出现两个平台词」改成「**URL 落在恰好一个平台上，且 channel 点名了它**」。现在 `X thread, not an issue` 被接受（`20-15` 绿），而「URL 在一个 channel 从没点名的平台上」仍然红（`20-20`）。
3. **消息又把形状说成存在**：`.1234Z`（真实时刻、格式不收）、`24:00`、小写 `t`/`z`、年份 <1000 都被说成「不存在」。现在拆成两句：形状不对 → `is not written as an ISO-8601 instant …`；形状对但值不可接受 → `names an instant this checker cannot accept …`（并说明可能是「不存在」或「超出支持范围」）。

顺手修的两处低危：`judgeNextChange` 在 `previous` 是数组时会把 `function at() { [native code] }` 当时间戳打印；`judgeDistTags` 多传一个包会让绿字说「all 5 package(s)」（现在多余条目直接判红，绿字只数本项目的四个包）。

**七条控制 + 终跑**：`20-00`（`drafts:[{}]` 不崩、产物照常）· `20-05`（裸日期）· `20-10`（`2026-02-30`）· **`20-15`（提到别的平台被接受）** · `20-20`（URL 平台未被点名）· `20-25`（`+01:00` 仍过）· `20-30`（未来）→ 全部按预期；终跑 `listing-2026-11-02T20-40-00.000Z.json` **15/15**。七次还原全部 `restored=true`。

**仍然开着（新增）**：`registry.posted_on` 与 `--posted-on` 是两份手写日期，仓内没有断言比较它们是否同一时刻（`T-837`）。
