## 2. 为什么这两项值得先做（不是「抄得爽」）

1. **CASE-10364 / CASE-10759 的真实痛点不是「被拒」**——stderr 已经说了被拒；痛点是「这份旧 `dsh-tools` 是谁带进来的」。原讨论的源码级回复明确说，缺的就是这一行。
2. **#10364 的静默变体我们原来完全接不住**：旧副本版本够兼容 → 全部 admission 通过 → 宿主启动 → 每个工具调用挂在模块级单例被求值两次。这正是 Maven 的 classpath 双版本问题，而 `dependencyConvergence` 的呈现方式（两条路径 + 两个版本）就是可行动的最小信息。
3. 两项都不需要真机、不需要网络、不需要新门——是能立刻被现有 9 门和 91 条测试压住的范围。

## 3. 对抗性审核

| 攻击 | 结果 |
|---|---|
| 只剩一份副本 | `duplicates` 为空、无来源行（e2e 第 3 条），不产生噪音 |
| 两份副本版本相同（pnpm 硬链正常形态） | 不出结论（单测），避免把正常布局报成问题 |
| 把来源字段改成 `peerDependencies` | 不输出「declared by」——peer 不落地副本（单测） |
| 声称「我们做了 npm audit 式扫描」 | `docs/09` §3 明确拒绝：不做安全背书（严禁行为 2） |
| 声称 attw 矩阵已实现 | 表中标 ⬜ 设计 + 前置条件（先实测 loader 解析模式），不写成已交付 |
| 把绝对路径写进 SSOT | 副本路径一律相对 DSH home（`profiles/...`），e2e 断言 temp root 不出现在 JSON |

## 7. 独立对抗性复核与纠正（R8 交付后）

外部只读会话逐条证伪，结论 **PARTLY CONFIRMED**；5 项真缺陷当轮修掉：

| ID | 严重度 | 观测 | 处置 |
|---|---|---|---|
| F1 | 高 | 同版本双副本仍被 `audit`/SSOT 报出（`kind: same-version`），与「同版本静默」冲突 | 扫描器只产出 `different-versions`；新增 e2e 断言同版本无输出 |
| F2 | 高 | `devDependencies` 被当来源，而依赖方的 devDeps 根本不安装 | 来源字段按「真的会落地副本」收紧（`dependencies` / `optionalDependencies`；profile 自身另含 devDeps） |
