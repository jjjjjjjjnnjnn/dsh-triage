## 2. 正确性

**PASS。** 三组可判定的断言：

1. **分段之和等于整步墙钟**（误差 ≤ 70ms）：

   | run | `steps[boot].ms` | 段之和 | 差额 |
   |---|---|---|---|
   | 模板 + 正常夹具 | 15741 | 15748 | +7 |
   | 复制组合 + 正常夹具 | 16217 | 16216 | −1 |
   | 永不 settle | 48384 | 48453 | +69 |

2. **差额被解释，且与 R21 的猜测不同**：正常候选 = sample 6.3 + settle 1.0 + readiness 0.04 + **render 4.7** + **杀树 2.2–2.7** + 杀后 1.2；不可判 = sample 19.1 + **替换等待 20.3** + settle 1.0 + render 4.5 + 杀树 2.2 + 杀后 1.2。R21 写的「≈25s（boot + settle 15s）」与「≈43s」**都是错的**，本轮以实测改正（`wait_ms 16.1s` 是 hook 自己的 settle，已含在 sample 里；多出的 20.3s 是执行器等一份可判样本的替换窗口）。

3. **凭据审计是双向的**：
   - 对照组（不注入凭据）：假 registry 收到 2 个请求、`authorization` 出现 **0** 次；
   - `user-npmrc`：`404` 与 `401` 两种应答下 token 都真的上了线（各 2/2），而**今天的沙盒 0/2**——这是第一次用请求头（而不是 pnpm 日志）证明 R20 的修复有效；
   - `global-npmrc` / `pnpm-own-rc` / `pnpm-home` / `corepack-home`：旋钮在 launcher 路径下**根本未被读**（带 `registry=` 的 `routed` 组也拿不到任何流量），两种应答一致。

## 3. 可复现

**PASS。**

- 分段：一条命令重放（`record_probe` 三个 label），产物含 10 段读数；
- 审计：`node scripts/audit_credential_sources.mjs --dsh-main <bin.js> --stamp <iso>`，30 次 launcher 运行 + 1 次 seed，全部离线（假 registry 在 127.0.0.1），退出码 1 = 发现泄漏；
- 两个真机负对照：`slow-overrun`（永不 settle）与 `strict`（源自带严格 workspace）分别锁定「不可判」与「组合未更新」两条路径。

## 4. 合规与许可

**PASS。**

- 审计脚本**不读任何真实凭据文件**，token 是本脚本写进临时目录的合成串（`probe-SYNTHETIC-token-not-real`），产物只留布尔与计数；
- 沙盒**不批准任何构建**（ADR-0007 第 2 条）；`strictDepBuilds: false` 只把错误降为提示，被跳过的包逐个公开；
- 本轮无新外部候选、无 vendor 条目，`quarantine/` 未动。

## 5. SSOT 一致

**PASS。**

- 四份新产物（3 份分段 + 1 份凭据审计）全部被 `audit/step_reviews.json` 引用，sha256 由门 `step-review` 重算；
- **111 份产物 / 126 步台账**全部可追（`gate_ssot` 与 `step-review` 的 orphan 检查都绿）；`HANDOFF` §2 的数字（**265 测试** / 111 产物 / 126 步）来自 `pnpm test` 与台账本身，不是手写估计；
- ADR-0006 的「实测纠正」段、spec §4 的分段表、`record_probe` 的 `limits[]`、`d2_report` 的 `wall_clock.note` 四处数字**同一套**（≈16s / ≈48s）；
- `BS-29` 的 status 与 `docs/adr/0004` §3 的 R23 修订段一致：只到「审计过的来源里只有 user config 会被读」，未越级声称。

## 6. 对抗性（本轮真的会错的地方）

| # | 注入/反问 | 结果 |
|---|---|---|
| A1 | **「用 pnpm 的日志判断有没有凭据外发」** | 反例成立：实测「合成 token + 真实 userconfig」**不打印** `An authorization header was used`。照这条准绳，一个活着的来源会被判成「没问题」。已改成假 registry 记请求头，并把这条写进 spec §8.6 与坑表 |
| A2 | **「假 registry 就在同进程里，用 `spawnSync` 起 launcher 就行」** | 反例成立：`spawnSync` 阻塞事件循环，服务器永远答不了，pnpm 挂到被杀（真踩三次 90s）。改为异步 `spawn` + `await close` |
| A3 | **「`global-npmrc` 没泄漏 = 我们挡住了」** | 反例成立：`routed` 组（源自己带 `registry=`）也拿不到流量，说明是**旋钮未被读**，不是我们挡的。产物区分 `knob_honored` 与 `leaks_today`，不许把两件事混成一件 |
| A4 | **「`404` 模式干净就算干净」** | 反例成立：凭据可能只在被挑战时发。加了 `401` + `WWW-Authenticate` 模式，两种模式各测一遍 |
| A5 | **「不可判 ≈48s 是因为 settle 15s」** | 反例成立：`wait_ms` 16.1s 已含在 sample 里；真正多出的是**替换等待 20.3s**（`sampleWaitMs − sampleMtimeMs`）。分段读数把两者分开 |
| A6 | **「分段只是记录，随便加个字段」** | 反例成立：分段之和必须与 `steps[boot].ms` 对齐（本轮三份误差 ≤70ms），否则「差额有解释」又是空话。spec §4 已写成硬规则：**新增 await 必须加段** |
| A7 | **「`strictDepBuilds: false` 会不会只是把错误藏起来」** | 反例部分成立：它会掩盖「有包没构建」这个信号，所以 ADR-0007 要求被跳过的包必须逐条进 `install.ignored_packages`，且该设置只在源 profile 没有 workspace 文件时写入 |
