## 3. 对抗性（本轮自己打自己的枪）

1. **「被写成 blocked 的慢候选」根本不是慢，是我们自己的端口**：`netsh` 显示本机 TCP **53461–53560** 被排除，plan 的哈希正好选中 **53506**，`webserver` 行 `listen EACCES` → 整棵树 `startup failed`。修后同一候选 `go`（5.9–6.8s）。**教训**：先问「这个失败形状会不会是我们造成的」，再改判据。
2. **排除段会在会话中途变化**：15:05 还能起（193 行 / 行 active），15:20 之后连续 3 次 EACCES。所以端口不能是常量或摘要 —— 一次性的「换个端口」修不好这类缺陷。
3. **`inactive context` 不是「树慢」，是我们的 fiber 被 unload 了**：读 Cordis 源码确认 `_unload` 会把 `fiber.store` 置空、服务回来后**重跑 apply**。因此「在同一 task 里重试」是假修复；真正有效的是代际保护 + 等一份可判样本。
4. **修完必须还能红**：N20（settled + 端口静默 → `blocked`）与两条真机负对照都在，防止「全都变 unknown」这种更糟的投降式修复。
5. **`startup failed` 之后还等满 120s**：launcher 已经判死，我们却把 126s 记成「boot 超时」。现在一出现就收敛（~6s），并把 launcher 原文写进产物。

## 5. 口径（对外只能说这些）

- 「**在一台本机 Windows 上**，真实候选 `dsh-whale-widget@0.4.2` 与 `dsh-plugin-model-proxy@0.1.6` 各真跑一次，都 `go`；boot 6.2–6.9s；失败清理 7/7」——不能说「成功率 100%」（n=2）。
- 「`startup failed` 时不归因给插件，除非 launcher 自己说明是插件；端口被拒归探针」——不能说「probe 已经不会误判」。
- 「R16 矩阵里 whale-widget 的 `blocked` 是**我们的端口选错**造成的」——这是本轮最该记住的一条。
