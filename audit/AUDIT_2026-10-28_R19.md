## 2. 正确性

**PASS。** 三个可判定的断言：

1. **归因不是猜的**：R19 spike 先抓真实输出再写规则。实测结论（F34/F35）：
   - `dsh: plugin command failed; diagnostics: <…>/pnpm.log` 指向的文件**只有 67 字节**（`Command failed with exit code 1: pnpm add …`），**没有** `ERR_*`；
   - 真正的 `Error: ERR_PNPM_IGNORED_BUILDS` 与 `Ignored build scripts: …` 只在 launcher 的 **stderr**；
   - stdout 同时打印 `+ @aiwayds/dsh-cron 0.6.1`——所以这个「装不上」的候选**其实装上了**，死在 pnpm 11 的 build-script 审批策略。
   提取顺序因此是「launcher 优先、诊断日志兜底」，并把 `source` 写进产物（`launcher` / `diagnostics-log` / `none`）。
2. **面板与 CLI 同源**：`GET /api/audit` 返回的就是 `auditJsonPayload()` 的产物；冒烟把面板结果与 `audit --json`（同 profile + 同 snapshot）逐条比对，**8 条 inventory 结论全等**。
3. **D2 复算**：真实 **13**（12 `go` / 1 `blocked`）· 可靠性 **20/20** · 清理 **20/20** · 形状 **6** · 通过率 **0.923**（Wilson **0.667–0.986**）。

**本轮自己抓到的三个错（都在提交前修掉）**：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| `key_line` 只取码行 | 文案变成「code ERR_PNPM_IGNORED_BUILDS: Error: ERR_PNPM_IGNORED_BUILDS」——与退出码一样是死胡同 | 码行没有解释就去下面找第一条 `label: detail`（`explanationFor`） |
| 把 harness 行当原因 | `synthetic-missing` 的 `key_line` 曾是 `dsh: plugin command failed; diagnostics: …`——launcher 在说它自己，不是原因 | 前向扫描跳过 `^dsh:` 与 `help:/hint:` 行；单测用实测夹具锁住 |
| 成功安装也留「诊断」 | 夹具（本地路径）`go` 的产物写着 `key_line: "Already up to date"`，看起来像失败 | `runInstall`：`exit 0` 时 diagnosis 恒为 `{null,null,'none'}` |
