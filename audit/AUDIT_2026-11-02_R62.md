## 2. 根因：四处半缺陷，全在**度量**这一侧

| # | 缺陷 | 为什么它能骗过人 | 修法 | 证据 |
|---|---|---|---|---|
| 1 | **`loading` 被当成终态** | 加载态走的是**失败视图**（`data-triage-tab="upgrade-error"`, `kind="loading"`），探针的终止条件是 `present === true \|\| error === true` → 第二轮采样（≈500ms）就 break | 「什么算已经回答了」抽成纯函数 `judgeUpgradeView` / `judgeTabView`，`loading` / `pending` 一律**不算判** | `scripts/lib/ui-probe.mjs` · `tests/unit/ui-probe.test.ts` |
| 2 | **跑不到底就写 `failed`** | 「没等到答案」和「屏幕坏了」被写成同一句话，读者只能猜 | 超预算 → **`unmeasured`** + 一句「等了 Nms，没等到答案，因此什么都不声明」 | `describeNoAnswer()`；NC-A 产物 |
| 3 | **页面内诊断永远返回 `null`** | `evaluate()` 把非 JSON 字符串 `JSON.parse` 掉了 → 唯一能回答「浏览器是不是被路由挡住」的那次测量，**什么都没记**（R61 产物 `direct: null`） | 表达式返回 JSON；`evaluate()` 不再吞字符串 | `record_client_serve.mjs` |
| 4 | **marker 被二次解析成 `null`** | `evaluate()` 已经解析过 JSON，代码又跑了一次 `JSON.parse(String(obj))` → `'[object Object]'` → 抛 → `null` | 对象直接用，字符串才解析 | 12:39 那次：四桶在屏、`same-source` 仍 `unmeasured` |
| 5 | **步骤 `status` 被证据覆盖** | `record(..., upgradeDirect)` 里的 `status: 200` 盖掉了 `'passed'`；产物里出现 `"status": 200`，任何读 status 的门/人都读错 | 改名 `http_status`；detail 写真实 URL | 旧产物 `client-serve-2026-11-02T14-40-00` |
| 6 | **`visible` 把 `pending` 写成 `passed`** | `body === 'pending'` 落到 else 分支 → `passed`，detail 还写「rendered the summary view」 | `pending/loading` → `unmeasured` | 12:49 那次的 `visible` 原文（见 §4） |

## 3. 产品侧改了两处（都不动判据）

1. **「进行中」与「失败」分开标记**：加载态改为 `data-triage-tab="upgrade-loading"`（`kind` 仍写 `loading`），
   失败态保持 `upgrade-error`。理由不是「为了好测」——`upgrade-error` 这个名字本身就在说「出错了」，
   而用户看到的是「正在读取」。**旧 bundle（registry 上的 0.3.1）不带这个标记**，所以探针里保留了
   「`upgrade-error` + `kind=loading` → 读成 loading」的映射，升级期不会重现这个 bug。
2. **Host 的悬挂定时器**：`Promise.race` 的 10s 上限定时器从不 `clearTimeout`，每次点击都在 Host 进程里
   留一个活到 10 秒的定时器。现在 `finally` 里清掉。

**根因**：`record_publish` 的「匿名安装」走的是 npm 的 `install-v1` 文档，而它由**另一套读副本**服务；
0.3.2 这次它比写路径晚约 **4.5 分钟**。`release:publish` 把取证卡在 publish 之后几秒，于是**每次发布都会假红**。

**修法（等，而不是放宽断言）**：`scripts/lib/registry-wait.mjs`

- `looksLikePropagationLag` —— 只认 `notarget` / `ETARGET` / `No matching version` 这类形状；
- `shouldRetryInstall` —— 只在「形状对 + 预算还有」时重试，默认 **5 分钟**，**最多 40 次**；
- **凭据错误（E401）立刻出结论**：等五分钟再报同一个错，只是把答案推迟；
- 产物新增 `install.attempts` / `waited_ms` / `wait_budget_ms`，等待真的发生时再记一条
  `registry-propagation`（正常 20 项的形状不变）；
- `describePropagationWait({settled})`：**预算花完仍是同一个答案 = 真失败**，句子必须这么说。

**证据**：9 条单测（`tests/unit/registry-wait.test.ts`）+ 一次真机正对照
（`--version 9.9.9 --wait-registry-ms 3000` → `2 attempt(s) over 16969ms` + 「after 16969ms it still did,
so this is a real failure, not a wait」）。第一版正对照的句子在失败分支说了「got a real answer」，被自己抓到，
产物 `publish-2026-11-02T14-20-00` 保留、14:22 那份取代它。

**边界**：4.5 分钟是**这一次**的观测；5 分钟预算是**上限**，不是承诺。副本更慢时它仍会红——那时红是对的。

**发布件里到底有没有这轮的功能（手读，可复跑）**：`npm pack dsh-triage@0.3.2` 解开后，
`package/client.js` 里 `data-triage-action: 'upgrade'`（第 365 行）、`data-upgrade-bucket`（406）、
`data-triage-tab: loading ? 'upgrade-loading' : 'upgrade-error'`（435）都在。**这条是手读，不是产物**：

## 10. 续：文案检查器里一条「永远通过的断言」

收口时把 `--tests` 传进 `check_listing`，输出是 **`0 claim(s) all equal 632`** —— 而同一份 README 里
同时写着「623 个测试」和徽章 `tests: 542 pass`。原因：正则是

```
(\d{2,4})\s*(?:个)?(?:测试|tests?)\b
```

`\b` 是 **ASCII** 词边界，`测试` 是宽字符，它后面永远不成立。所以这条断言从写下来那天起**一条声明都没找到**，
而「找到 0 条 = 没有陈旧声明 = 通过」。徽章的 `542` 因此僵了三轮。

- **修法**：匹配三种写法（中文 `N 个测试` / `tests: N` / 徽章 `badge/tests-N`）；
- **新增守卫** `test-count-is-not-vacuous`：传了数字却找到 0 条声明 → 红。这条守卫是本轮唯一新增的断言
  （`check_listing` 14 → 15），它存在的理由就是「空转的门」比「红门」更危险；
- **两条红产物**：`listing-2026-11-02T14-27-00.000Z.json`（徽章 542 被点名）、
  `…T14-28-00.000Z.json`（徽章改完后正文 623 被点名）；终跑 `…T14-29-00.000Z.json` **15/15**；
- **`--tests` 不传时**两条断言都写 `skipped (no --tests passed)`，不假装通过。

**这是本轮同一个主题的第四次**：R50「检查没跑起来」、R51「pending 当结论」、R61「loading 当失败」、
R62「空转的断言」——**四次都是「没有观测」被当成了「观测结果是好的」**。
