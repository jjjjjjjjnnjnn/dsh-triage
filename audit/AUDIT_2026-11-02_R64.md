## 2. 四件事

### 2.1 X 线程发出去后，台账跟着落地

`docs/distribution/T-810/registry.json` 的 `03-x-en.md`：`draft` → `posted`，`posted_url` =
`https://x.com/jjjj1955714/status/2117306628227940741`（去掉了分享参数），`posted_on` =
`2026-11-02T17:36:00.000Z`。

**时区是第一处真坑**：用户报的是「2026年11月02日 18:36」，而这台机器是 **UTC+1**（`local - utc = 01:00:00`）。
按国内习惯当成 +08 会写成 `10:36Z`——差 7 小时。`posted_on` 差 7 小时不会报任何错，只会把 D5 的 14 天窗口
整体挪早。这正是第 13 条断言存在的理由。

仓内的 `03-x-en.md` 仍是英文备选版；**中文主选稿在 `git stash`（`stash@{0}`）**——用户明确要求「稿子不用管，
stash 起来」，所以没有提交，registry 里用 `note` 字段把这件事写清楚（台账不能只记「posted」而藏起版本差异）。

### 2.2 第 13 条：从「只能是 discussion URL」改成「域必须与 channel 声明一致」

**旧规则让事实无法登记**：`posted_url` 必须匹配 `^https://github\.com/<owner>/<repo>/discussions/<n>$`——
X 的帖子根本录不进去，于是台账只能停在 `draft`，与「已经发了」不一致。R56 修过同型问题（登记写明「已发布」
但字段是 `draft`），所以这里不重复那个错误。

**新规则**（只精确化，不放宽）：

| 平台 | channel 必须含 | URL 必须匹配 |
|---|---|---|
| `github-discussion` | `discussion`（不分大小写） | `https://github.com/<o>/<r>/discussions/<n>`（允许 `#` / `?` 尾巴） |
| `github-issue` | `issue` | `https://github.com/<o>/<r>/issues/<n>` |
| `x` | 独立的 `X` 词或 `twitter` | `https://(www.)?(x\|twitter).com/<handle>/status/<id>` |

外加两条收紧：① **channel 没有点名任何平台 → 红**（否则这条断言对它是空转）；② `posted_on` 必须是
**带时区的 ISO instant**（`2026-11-02` 这种裸日期 `Date.parse` 能过，却会把窗口挪最多 24 小时）。

顺手把 `06/07/08` 三条回帖草稿的 `channel` 补上 `GitHub Discussions`——它们本来就是回帖，补上之后将来真发时
不需要再改一次 registry 才能通过。

**三条定向负对照（各自真红，产物保留）**：

| 产物 | 构造 | 检查器原话 |
|---|---|---|
| `listing-2026-11-02T17-50-00.000Z.json` | X 的 URL + channel 说 GitHub Discussions | `posted_url is not a github-discussion URL (got "https://x.com/…")` |
| `listing-2026-11-02T17-55-00.000Z.json` | `posted_on = "2026-11-02"` | `posted_on is not a timezone-qualified ISO instant` |
| `listing-2026-11-02T18-00-00.000Z.json` | `posted_on = "2026-12-01T00:00:00.000Z"` | `posted_on is in the future` |

三条都用 **node** 改文件、每次跑完立刻写回原串并**复算 sha256 校验还原**（R56 用 PowerShell 改 JSON 时按 GBK
写坏过文件，导致循环零次、假绿通过）。

**这一条属于文案检查器的规则变更，不在 9 门冻结项里**，按 R52 / R56 的先例登记进 `audit/SIGNOFF.md`。

### 2.3 `record_publish` 新增 `dist-tags-agree`

`scripts/lib/dist-tags.mjs`（纯函数，7 条单测）+ `record_publish` 的一项检查：

1. 四包 `latest` **彼此相同**；
2. 且等于本次发布版本；
3. 且不指向**未发布**的版本（tag 悬空）；
4. 读不到 packument → `unmeasured`，**不是** agree（读不到时记三项「对」比记一项「不知道」危险得多）；
5. 有其它 tag（例如 `next`）指向真实版本 → 只报告，不判红。

**为什么补这个**：0.3.1（`core` 卡在暂存 → `latest` 指向装不上的版本）和 0.3.3（三包回滚到 0.3.2，
`signals` 已是 0.3.3）是**同一个形状**，而当时唯一的读法是「人眼看四行 `latest=`」。单测里两条负例就是这两次
事故本身。

### 2.4 升级日监听：`scripts/watch_next_release.mjs`

读 `@deepseek-ai/dsh` 的 `dist-tags.next`，与 `data/results/next-release-*.json` 里最近一次观测比对：

| 状态 | 条件 | 落产物 |
|---|---|---|
| `baseline` | 能读 + 无历史 | ✅ |
| `changed` | 能读 + 值不同（**含回滚**） | ✅ |
| `unchanged` | 能读 + 值相同 | ❌（不制造每日噪声） |
| `unmeasured` | 读不到 / 没有该 tag | ❌ **且 exit 2** |

**「读不到」不是「没更新」**：R52 曾经把 403 读成 `threads: 0`（「没人有这个问题」），R51 把 `pending` 当答案。
监听器最坏的行为就是在看不见 npm 的时候报平安，所以这条写死在纯函数里（6 条单测，其中一条专门枚举四种读不到
的形状）。

**它不跑卡片、不发帖**：卡片的数字来自本机 profile，在 watcher 里跑会让人以为那是所有人的机器。输出给的是命令。

真机：首跑 `baseline next=0.2.1-rc.5`（`data/results/next-release-2026-11-02T17-40-00.322Z.json`）→ 再跑
`unchanged`、零产物、exit 0；`changed` 分支在 `%TEMP%` 里用「先观测 `dsh-triage@latest`，再观测
`@deepseek-ai/dsh@next`」真跑过；死端口 → `unmeasured` + exit 2 + 目录为空。

## 3. 本轮自己抓到的三个缺陷

1. **时区**：见 §2.1。7 小时的偏差不会报错。
2. **`process.exit()` 紧跟 `fetch` 在 Windows 上崩**：首次真跑退出码是 **1**，stderr 有
   `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 76`——读取其实成功了，
   但任何调用方都会把它读成失败。改成 `process.exitCode` + 让事件循环自己排空。
3. **`--stamp` 用冒号**：我按产物名格式（`2026-11-02T17-50-00.000Z`）喂给 `--stamp`，检查器判「用法错误」
   exit 2。**exit 2 看起来像「断言没过」**，三次负对照因此空转了一次——这也是为什么负对照要打印检查器原话，
   而不是只看 exit code。

## 4. 边界（不许外推）

- `dist-tags-agree` 只证明**这一次读取时**四个 tag 一致；registry 分region 服不同内容就看不见。
- 监听器的 `changed` **不判断方向**（升级还是回滚都算变化），就报两个版本原值。
- `check_listing` 第 13 条只管「URL 与 channel 声明一致」+「时间是过去的带时区 instant」，不验证那个 URL
  真的能打开、也不验证 weibo/V2EX/B站 之类新渠道（新渠道要先把平台名写进 `channel`，再加一档规则）。
- 本轮**没有**发表任何内容：X 帖子是 HUMAN 发的，我只是登记。
