## 1. 结论

**CONFIRMED。四项全部落地，而且它们改变的是「能不能在 60 秒内试一次」，不是「判得准不准」。**

R47 把正门换成了「升级日」，但正门前面还有一道台阶：用户得知道该填哪个版本号。`upgrade --to <version>` 只接受精确 semver，而一个陌生人此刻并不知道上游 `next` 是什么——所以 R47 的卡片**结构上无法被第一次接触的人用到**。本轮把这道台阶拆掉，四件事各拆一层：

1. `--to next` / `--to latest`：目标从 npm `dist-tags` 解析，**解析值逐字交给同一个引擎**；
2. 没有 `--to` 时不再只打 usage，而是把「你当前是什么、可选目标是什么」说出来，**仍然 exit 2**；
3. `--card --out`：卡片能落成文件（粘贴到 issue / Discussion 的最后一公里）；
4. README 首屏直接放真机卡片，并用机器断言盯住它。

**唯一没做完的事在别人手里**：`npm publish 0.3.0`（HUMAN 的 OTP）。这让 README 的版本号在发布前**领先于 registry**——一条已知、且必须本轮关闭的窗口，写在 HANDOFF §3 第 1 条。

## 4. 过程里自己抓住的三个缺陷

1. **记录器的断言写错了，不是产品错了。** `record_upgrade_entry` 第一次跑 23/26，三条红全是「按 `current` / `targets` 这类英文标签匹配」，而记录器自己把 locale 设成 zh。修法是让断言认**语言无关的值**（版本号 + profile 名）与 zh/en 双写的「未知/读不到」——不是放宽断言。红产物保留。
2. **覆盖拒绝返回了 exit 3。** 判据写的是「目标已存在 → exit 2（用法）」，实现里所有写失败都映射到 `EXIT_UNAVAILABLE`。修法是把 `writeCardFile` 的失败改成带原因（`exists` / `unwritable`），由调用方分别映射 2 / 3。
3. **用 PowerShell 造负对照把中文 README 写坏了。** `Get-Content -Raw | Set-Content -NoNewline` 在本机做了 ANSI 往返，中文全毁；那次 16:25 的红产物**作废并删除**（它不是任何真缺陷的见证），改用专门的编辑工具重做两条负对照。这条写进反思：**构造负对照也要用不会改字节的工具**。

## 5. 诚实边界（必须一起读）

1. **`tag-missing` / `tag-not-exact` 没有真机见证**（`BS-45`）：真实 registry 上 `next` / `latest` 都存在且值都精确，所以这两条只有单测证据。产物 `limits[]` 里写明。
2. **「解析值逐字等于 registry」是时点断言**：产物锁的是 R48 那一刻的 `0.2.1-rc.4` / `0.2.1-rc.2`。上游改 tag 后旧产物不会自己变红，只能靠 `--fixtures` 复算 + 新轮重跑。
3. **Windows 上「目录只读」拦不住属主写入**：`T-808` 的第三类失败用「父路径是普通文件」（`ENOTDIR`/`EEXIST`）替代。**没有测过只读目录**，M6 C10/N18、BACKLOG、`limits[]` 三处都写明是替代构造。
4. **`improved` 仍然只有降级几何**（`BS-42`）：本轮没有、也不能改变它；卡片措辞仍是「目标版本会放行它」。
5. **卡片判的是声明层**：`likely-fine` 只表示「声明上不冲突」，不是「升级后真能跑」。
6. **0.3.0 尚未在 npm 上**：`npm publish` 是 HUMAN 动作；在 `record_publish` 变绿之前，README 的版本号领先于 registry。
