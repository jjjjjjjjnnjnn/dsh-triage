## 1. 发布：不是一条命令，是一条链

HANDOFF 原来的发布命令是 `npm publish -w dsh-triage --access public`。这条命令会发一个**装不上的包**，
原因有两个，都是实测出来的：

| 事实 | 证据 | 后果 |
|---|---|---|
| npm **不重写** `workspace:*` | `npm pack` 出 tarball → `tar -xOf … package/package.json` 仍然写着 `"@dsh-triage/core": "workspace:*"` | 用户 `npm i` 直接失败 |
| `@dsh-triage` 这个 **scope 不存在** | `npm org ls dsh-triage` → `E404 Scope not found` | 发 scoped 包 403/404 |
| npm 对写操作强制 OTP | `pnpm publish` → `ERR_PNPM_OTP_NON_INTERACTIVE`；`npm publish` → `EOTP` | agent 的非交互 shell 发不了 |
| 新 scoped 包发布后一段时间仍 404 | `npm i dsh-triage@0.1.0` → `404 @dsh-triage/probe`；同一时刻重发 → `cannot publish over the previously published versions` | 「发布成功」与「可安装」不是同一时刻 |

最终形态：**四个包按依赖顺序**（`@dsh-triage/core` → `signals` → `probe` → `dsh-triage`），
发布动作由 HUMAN 在交互终端完成（OTP 在 HUMAN 手里），agent 负责发布前预检与发布后验证。

**验证是匿名的**（`data/results/publish-2026-10-29T01-40-00.000Z.json`，20 项全绿）：

- 四个包的 registry `dist.integrity` 与本地 tarball 的 sha512 **逐字节相同**；
- registry 上的 `dependencies` 里 **没有** `workspace:` 残留；
- `npm_config_userconfig` 指向空文件（没有操作者 token）时，`npm install dsh-triage@0.1.0` 装回 **6 个包**；
- 装完 `dist/cli.js --help` 真跑出 9 条命令，`import('dsh-triage')` 拿到 `apply / loadBundleLayers / …`。

**不能说什么**：这只证明 registry 收下了包、陌生人能装能跑 CLI。它不证明 DSH Host 能加载 bundle
（那要靠 `probe` / `record_client_serve`），也不证明 dsh.so 已收录。

## 2. `BS-39`：ptc 折叠下的真机见证

做法：给 `ExtraPatchEntry` 加可选 `config`，用 overlay 把 `tools` 行改成 `mode: ptc`；
`record_agent_tool.mjs` 新增 `--tools-mode`，并在产物里记 `sandbox.tools_mode`。

**上游语义先读再写**：`ToolRuntime.Config = z.object({ mode: z.union(["native","ptc"]).default("native") })`；
而 patch 的 `config` 是**整块浅替换**（`applyEntryPatches` 里 `target[key] = value`），不是深合并——
所以产物必须记生效值，不能假设其余配置还在。

真机结果（`data/results/agent-tool-ptc-2026-10-29T03-05-00.000Z.json`）：

| 项 | ptc | native（对照，`03-20-00`） |
|---|---|---|
| `schemas()` | `[compat_verdict, working_directory, run_code]` | `[compat_verdict, working_directory]` |
| 三次调用路径 | **3/3 `via=definition`** | **3/3 `via=registry`** |
| 拒绝原因 | `unknown tool "compat_verdict": only run_code is callable directly — call compat_verdict from inside run_code` | 无（未被拒） |
| 结论 | go / blocked / unknown | go / blocked / unknown |

**真机打脸了两次**（都留在产物里，不改）：

1. `agent-tool-ptc-2026-10-29T02-30-00.000Z.json`（`outcome=failed`）：我按「ptc 下插件工具会从
   `schemas()` 消失」写了断言，真机证明**没有消失**——ptc 换的是调用路径，不是投影。若为了变绿去
   放宽断言，等于把部署事实改掉。
2. 同一份产物里三次 `registry_refusal` 全是 `[object Object]`：`describe()` 用 `String(error)` 处理
   非 `Error` 对象。已改为读 `code`/`name`/`message` → `JSON.stringify` → `Object.prototype.toString`。

**仍然没有证明**（写进 `BS-39` 与产物 `limits[]`）：① 模型会不会主动选这个工具；
② 在 `run_code` 程序内部调它能不能通（本轮只探了「模型直调被拒」这一条）；
③ 别的 ptc 部署（例如 ptc runtime 未装）是否同样拒绝。

## 3. 渠道：一个 `ready` 不等于一次提交

`market-channels-2026-10-29T02-00-00.000Z.json`：`npm.published=true`、registry 200 → **dsh.so 由
`blocked` 变 `ready`**（`blocker=null`）。`02-10-00` 追加了 `review_decision` / `merge_state_status` /
`merged_at`，因为「审过了」和「合并了」在产物里原本长得一样：

| PR | state | review_decision | merge_state_status | merged_at |
|---|---|---|---|---|
| #65 community-plugins | `open` | `null` | `BLOCKED` | `null` |
| #193 awesome | `open` | **`APPROVED`** | `CLEAN` | `null` |

`merged` 才是收录。`ready 4 · live 2 · merged 0` 是本轮唯一诚实的渠道读数。

## 4. 本轮的真发现

1. **npm 不重写 `workspace:*`** → HANDOFF 的发布命令会发坏包（已改写并进坑表）。
2. **scope 与 OTP 是两个前置**：`@dsh-triage` 需要免费公开 org；写操作强制 OTP，非交互 shell 报
   `ERR_PNPM_OTP_NON_INTERACTIVE`。
3. **staged publishing**：新 scoped 包发布后仍会 404 一段时间；此时重发得到 403
   「cannot publish over the previously published versions」——那是「已经有了」，不是失败。
4. **ptc 下 `schemas()` 仍列出插件工具**（第二次打脸）。
5. **`describe()` 把对象拒因写成 `[object Object]`**（探针自己的缺陷）。
6. **布尔被当成状态字符串**：`record()` 收到 `true` 时报表打印 `--`、`outcome` 也不数它，于是
   `agent-tool-ptc-2026-10-29T02-50-00.000Z.json` 在 `outcome=passed` 的情况下藏了一个未审步骤。
   已把 `record()` 变成硬断言。
7. **INDEX 引用门又抓到一次裸文件名**（§4 坑表里写着的那条）：本轮第一次 `gate --record` 因
   `index-references` 判红（`audit/AUDIT_2026-10-29_R40.md` 尚未创建 + 两个裸 `.json` 产物名 +
   一个带 `--tools-mode` 旗标的反引号 token）。修法是把产物写成完整 `data/results/…` 路径。
   **这次录制还撞上了第二个坑**：我用的 `--stamp 2026-10-29T03:40:00.000Z` 正是 R34 录过的时刻，
   于是把 R34-S2 引用的产物覆盖了（`step-review` 立刻报 sha 不匹配）。处置：`git checkout` 恢复原文件
   （sha `fc97d1d8…`）、删掉本次那份红产物（它没有也不可能被引用）、把「撞 stamp」写进本报告与坑表。
   **没有**为了留住证据去重造一次失败——那会是表演。

## 5. 对抗性（自问自答）

- 「发布成功」≠「能装」：证明方式是把 userconfig 换成空文件再装一次，并比对 registry 字节。
- 「`approved`」≠「收录」：产物把三列分开记，`live` 仍只数 OPEN。
- 「ptc 通了」≠「模型能用」：`run_code` 内部调用未测，写进 `BS-39` 与 `limits[]`。
- 「一条命令发布」是错的：五条坑里的任何一条都会让「一条命令」变成「一个坏包」。
