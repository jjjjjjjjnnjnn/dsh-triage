# AUDIT · R37（2026-10-29）`BS-32` 有载对照 + 一个真发现（T-321）

> 本轮做两件事：把「抖动从哪来」变成一次可复算的对照，并修掉对照过程中**被自己抓到**的一个真缺陷。
> 四轴结论 + 对抗性反例见 `audit/step_reviews.json` 的 `R37-S1…S4`。
> **阈值一字未动**：`--unsettled-timeout 20000`、hook `settle 15s`、readiness 5s、`boot→sample ≤20s`、
> `isUsableSample()`/`judgeProbe()` 的既有分支、`data/gold/`、`PROJECT_RULES.md` 铁律。

## 1. 有载对照（`BS-32` 的下一半）

| 批 | 条件 | 批数 | 真实观测 | `boot→sample` | 超预算 | 无产物 |
|---|---|---|---|---|---|---|
| 14:00 / 16:10 | idle | 2 | 24 | 3.7–6.2s，median **4.9s**，p90 6.0s | 0/24 | 0/40 |
| 14:30 / 14:50 | `--load 8`（实测 58–62% CPU 占用 / 24 逻辑核） | 2 | 24 | 5.8–8.3s，median **7.4s**，p90 7.8s | 0/24 | **1/40** |

- **怎么造的载**：`record_probe_matrix.mjs --load 8` 起 8 个 CPU-busy Node worker，整批期间常驻；
  占用率用 `os.cpus()` 的累计时间差算（**`os.loadavg()` 在 Windows 恒为 0**，用它就是把标签当读数）。
- **结论**：有载把中位数抬高约 **51%**（4.9s → 7.4s），**但没有把任何真实候选推出 20s**；
  13 个真实候选的结论在四种批里一致（唯一例外见 §2，是探针自身故障，不是候选）。
- **不能说什么**：这只是一种载荷（本用户 CPU 饱和）、一台机器、一个运行时；内存/磁盘压力、
  多个探针并发、Linux 上的行为都**没测**（`BS-40`）。

## 2. 真发现（T-321）：探针自己的临时目录失败，被记成插件失败

一批 **idle** 矩阵里 `real-unlag@1.12.5` 被记成 **`blocked`**：

```
boot: 37489ms · detail: EPERM, Permission denied: …\triage-live-Jvv54r
reasons: probe.boot-timeout {seconds: 37}
```

`triage-live-*` 是**探针自己的** scratch 目录。链条是：`rmSync(probeDir)` 抛 `EPERM`（Windows 持有句柄）
→ 异常逃出 `bootAndSampleHost` → 执行器把它记成失败的 `boot` 步 → 判据只剩「没样本 + 没打印 URL +
没 `startup failed`」这一条路 → `probe.boot-timeout` → `blocked`。

这是 R17「端口自伤」的同一类：**我们的环境问题被算成插件的问题**。修法（不改任何阈值）：

1. `host.ts`：scratch 的**准备**失败与**删除**失败都写成字段（`setupError` / `scratchCleanupError`），
   永不抛；`finally` 里的删除也只记录。**清理失败不再销毁已经拿到的样本**（原来一个 `rmSync` 就可能让
   一次成功测量变成异常）。
2. `exec.ts`：`boot` 步里任何异常都记成 `bootSetupError`（`runStep` 统一兜底），判据新增
   `probe.measurement-unavailable` → `unknown` + `missing.probe`；三件套断言一起 `unmeasured`。
3. 产物：`boot.setup_error` / `boot.scratch_cleanup_error` 落账（`scripts/record_probe.mjs`）。

**那条红产物原样保留**（`probe-matrix-2026-10-29T15-30-00.000Z.json`）——它是唯一真机见证，删掉就没有证据了。
负对照是 `tests/unit/probe-exec.test.ts` 的 N24 / N24b：`setupError` 与「boot 步抛异常」都必须是 `unknown`。

## 3. 四轴

- **正确性**：`probe.measurement-unavailable` 只出现在「我们自己的文件系统失败」这一条路上；
  `probe.boot-timeout` 仍保留给「Host 真的没起来」（N22 仍红）。有载/空载的对照用的是**同一份 plan、
  同一条引擎、同一台机器**。
- **可复现**：`record_probe_matrix --load <n>` 一条命令；`stability_report` 只吃已落盘矩阵，不设 gate；
  两个脚本都只依赖 Node 内置模块。
- **合规**：无新依赖、无外部数据；矩阵与报告都在 `data/results/` 带 `.sha256`。
- **SSOT**：`conditions[]` 与 `runs_without_artifact` 让「有载」与「没判定」都不能被读成别的东西；
  `stability_report` 的 4 条契约测试仍全绿（新增字段不动既有语义）。

## 4. 对抗性

1. **「有载更慢」会不会只是批与批之间的自然差异？** 两批 idle 与两批有载是交错跑的（14:00 idle →
   14:30 有载 → 14:50 有载 → 16:10 idle），中位数 5.1 vs 7.4 在两批内都成立；但它仍是**观测**，
   不是「负载 ≥58% 必然慢 45%」的定律。
2. **把 15:30 那批从对照里拿掉，是不是挑数据？** 它留作 §2 的缺陷见证，**不进对照**（那批的
   `real-unlag` 是我们的 bug，不是负载效应）；报告里两条线各自可查。
3. **`observed_busy_percent` 会不会是自证？** 它来自 `os.cpus()` 累计时间差，是**整机**读数（含矩阵
   自己），不是 worker 自报；而且 `--load 0` 的批是 null，不会被写成 0%（`BS-40` 记录的是有载批里
   1 次无产物，也没被藏）。
4. **修 T-321 会不会把真失败也变成 `unknown`？** N22（无 URL 的 boot 超时）仍是 `blocked`，
   N20（settled 树 + 静默端口）仍是 `blocked`；新增分支只在 `bootSetupError` 非空时生效。

## 5. 未做 / 边界

- 只测了一种载荷、一台 24 逻辑核的 Windows、0.2.1-rc.4；`BS-40`（有载 1/40 崩溃，未复现未归因）、
  `BS-41`（句柄占用无法按需复现）。
- **删掉的两份中间报告**：`stability-2026-10-29T15-10`（3 矩阵：1 idle + 2 有载）与 `15-50`
  （4 矩阵，但把缺陷批当成了空载侧）。它们**从未被任何结论引用**，且都被 `16-30` 取代；
  删的是「本轮自己刚生成、尚未入库」的中间件，与 R31 删中间录制同类。**最终报告只有一份**：
  `data/results/stability-2026-10-29T16-30-00.000Z.json`（两批 idle + 两批有载）。
- `BS-32` 的**结论**：抖动的主因目前只能说「机器条件显著影响中位数」，不能说「抖动全部来自负载」——
  R27 的 22.5s 是旧口径（判最终样本），与本轮不可相减。
- 没有为了变绿放宽 `boot-budget`，也没有删任何红产物。
