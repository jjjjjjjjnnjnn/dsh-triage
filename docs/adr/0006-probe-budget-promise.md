# ADR 0006 · probe 的「20s」到底承诺什么（`BS-28` / T-311）

> **状态**：**已采纳（2026-10-28，第 1–3 条）**。HUMAN 会话内原话：「同意，继续」。**方案 A / C 未授权**，因此默认 `settle 15s` / `--unsettled-timeout 20000` 保持原样，未动任何判定。
> **影响面（已落地部分）**：`docs/specs/M3-probe.md` §4、`scripts/d2_report.mjs` 的 `timing.wall_clock`、`scripts/record_probe.mjs` 的 `limits[]`。**未落地**：默认窗口、D2 判据（均需方案 A/C 授权）。

## 背景（全部实测）

1. **M3 的出口门禁写的是 `boot → sample ≤ 20s`**（`docs/specs/M3-probe.md` §4，M3 出口门禁）。
2. **「树未稳定」的窗口默认也是 20s**（`--unsettled-timeout 20000`，R17 引入），其用途是给「慢但会好」的候选一次机会，但**该窗口只能产出 `unknown`**。
3. **永不稳定的一棵树实测 ≈21s**：`fixture-slow-overrun` 顶层 await 20s → `boot(≈5s) + hook settle 上限 15s ≈ 21s`。把窗口从 20s 降到 8s 只省 ~2.5s（19.6s / 21.3s 两次实测），因为**主导项是 settle 上限 15s，不是那个窗口**。
4. **R18 的 19.1s 是运气**：同一夹具同参数，R19 两次跑出 19.6s 与 21.3s。R18 的 D2「全量预算通过」因此不成立于同一份夹具。
5. **R19 已签的口径只解决了一半**：`d2_report` 的 `boot-budget` 现在只判 `real:true`（真实候选 12/12 在 20s 内）。**产品侧没解决**：一个真实的、真的需要 >15s 才稳定的候选，用户仍会等 ~21s。

## 决定（提议）

**「20s」是「测量预算」，不是「墙钟承诺」。** 具体三条：1. **保留测量口径**：settled 树 `boot→sample ≤ 20s`（不变），unsettled 树仍走 15s settle + 可配窗口，结论仍是 `unknown`（不变）。
2. **把墙钟写进 spec 并**在产物里自曝**：`limits[]` 增加一条「an unsettled tree is returned by ≈25s (boot + settle 15s), not 20s」；`d2_report` 的 `timing` 段同时给 `real_within_budget` 与 `fixtures_over_budget`（R19 已做），并新增 `wall_clock_max_ms`（不设判据，只记录）。
3. **产品文案改口径**：对外只说「可判的候选 20s 内出结论；需要更长稳定期的候选会以 `unknown` 返回，通常在 25s 内」。不许写「任何一次 probe 都 ≤20s」。

## 不采纳的方案（以及为什么）

| 方案 | 为什么不 |
|---|---|
| **A. 把 hook settle 15s 降到 10s** | 最省事，但会**少测**：实测 `slow-plugin`（导入 6s）需要 `wait_ms 7.3s` 才稳定；10s 窗口会把 10–15s 才会稳定的真实候选从「测得出来」变成「unknown」。用「更少的测量」换「更好看的时长」是本项目明确反对的交易 |
| **C. 两阶段：20s 先回 provisional，再续采** | 工程上最接近「既快又全」，但要改 hook 的写出协议（两次写样本 + 代际保护）、执行器要能接受「先 unknown 后升级」的样本，并重跑 R17/R18 的全部时序负对照。**不是不行，是超过一轮的预算**；建议作为 T-312 单独立项 |
| **D. 不改，继续只报「≥90%」** | 会把「一次 21s 的等待」藏在一个百分比后面。D2 判的是可靠性，不是用户等待时间；两者不能互相顶替 |

## 后果

- **诚实**：用户看到的时间与文档一致（「可判的 20s；不可判的通常 25s」），而不是「有时 21s，文档说 20s」。
- **代价**：spec §4 要与 `limits[]` 同改，否则又是一处口径分叉；`d2_report` 多一个 `wall_clock_max_ms` 字段（不设门）。
- **不做的事**：不改任何判定；不改 `unknown` 的含义；不因为这条 ADR 放宽 D2。

>
> **同日晚些时候的实测纠正（本条优先于上面那句「≈25s」）**：`d2_report.timing.wall_clock` 第一次真算出来是 **42701ms**。逐 run 看：正常 `go` 候选的 `boot` 步 = **22.1–25.3s**（而 `boot→sample` 只有 9.6–12.2s），永不 settle 的夹具 = **42.7s**。也就是说：
> 1. 「20s」连**正常候选的等待时间**都没覆盖——预算量的是 `spawn→sample`，不是用户等的墙钟；
> 2. 我原先写的「不可判 ≈25s」是**错的**（实际 ≈43s），已按实测改正；
> 3. 差额（正常候选多出的 ~12s、夹具多出的 ~21s）**还没解释**——别猜成「settle 15s」就完事。已开 **T-314**：给 `boot` 步加分段计时（spawn / hook 写样本 / settle / readiness / 杀树 / 删除），再决定文案与是否需要优化。
>
> ## 附：T-314 实测结果（2026-10-28 晚，R23）——差额已解释，且**再次**改正文案
>
> `boot` 步现在逐步计时（`timings.bootSegments`）。四份真机产物：
>
> | run | `boot` 步 | sample | **替换等待** | settle | readiness | **render** | **杀树** | 杀后等待 | 删除 |
> |---|---|---|---|---|---|---|---|---|---|
> | 模板 + 正常夹具 | 15.7s | 6.3s | 0.24s | 1.01s | 0.04s | **4.73s** | **2.21s** | 1.21s | 0.002s |
> | 复制组合 + 正常夹具 | 16.2s | 6.3s | 0.19s | 1.01s | 0.04s | **4.72s** | **2.71s** | 1.21s | 0.001s |
> | 永不 settle（`slow-overrun`） | **48.4s** | 19.1s | **20.27s** | 1.01s | 0.04s | 4.50s | 2.20s | 1.22s | 0.001s |
>
> **结论（推翻上文第 3 条的猜测，也推翻「≈43s」这个上界）**：
>
> 1. 正常候选的差额是 **render ~4.7s + 杀树 ~2.2–2.7s + 杀后固定等待 1.2s + settle 1.0s**，与 settle 上限无关；
> 2. 不可判的树是 **48.4s，不是 43s**：主导项是**「为一份可判样本再等一整个替换窗口」= 20.3s**（`sampleWaitMs 39.4s − sampleMtimeMs 19.1s`），而 hook 自己的 settle（15s 上限、本次实测 16.1s `wait_ms`）**早已含在 sample 里**，不是额外项；
> 3. 因此对外口径应为：**可判的候选 ≈16s 出结论；需要更长稳定期的候选 ≈48s 返回 `unknown`**。旧的两处数字（25s、43s）都作废；
> 4. **阈值仍然一个都没动**。要不要把替换窗口压到「剩余预算」是 T-311/T-312 的授权范围，本轮只交付测量与文案。
