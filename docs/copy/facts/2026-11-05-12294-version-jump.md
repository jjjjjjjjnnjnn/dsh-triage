## 精确数字（全部来自上面那份产物）

一台 **真实 profile**（`profile: web`，正在跑 `0.1.0-rc.6`），目标 `0.2.2-rc.1`：

| 项 | 值 |
|---|---|
| 单元总数 | **130**（2 bundle + 128 行） |
| `would-be-denied` | **128** |
| `cannot-tell` | **2**（`row:hmr`、`row:timer`，`missing.peer-declaration`） |
| `improved` | **0** |
| `likely-fine` | **0** |
| 今天（`0.1.0-rc.6`）已被拒 | **0** |

**机制**（同一份产物 `units[].unmet[]` 的字段，不是推测）：

- 128/128 个被拒单元，挡它的要求都是 `^0.1.0-rc.<n>` 这种 **caret 区间**；
- 其中 `@deepseek-ai/dsh-invariants@^0.1.0-rc.6` **出现在全部 128 个单元**上；
- 全部 unmet 要求合计 **751** 条，去数字后**形状只有一种**：`^<semver>`。

`^0.1.0-rc.6` 按 semver 的含义是 `>=0.1.0-rc.6 <0.2.0-0` —— **任何 `0.2.x` 都在区间外**。
所以这不是「0.2 是另一个产品」，是**插件声明的区间把 0.1 锁死了**：只要上游把 minor 从 `0.1` 抬到 `0.2`，
所有用 `^0.1.0-rc.N` 声明的行都会被构造性地排除。

复算（离线，给确切版本号不读网）：

```console
npx dsh-triage upgrade --to 0.2.2-rc.1 --card
```

```console
node -e "const a=require('./data/results/upgrade-2026-11-05T18-40-00.000Z.json');const d=a.units.filter(u=>u.bucket==='would-be-denied');console.log(a.units.length,d.length,d.filter(u=>u.unmet.some(r=>/^\\^0\\.1\\.0-rc\\.\\d+$/.test(r.range))).length,d.flatMap(u=>u.unmet).length)"
```

## 可以说什么

1. 让他自己那条命令跑一遍 —— 数字会不一样（不同机器、不同插件），但**形状**是一样的；
2. 指出挡住的不是「新版本」，是**声明里的 `^0.1.0-rc.N`**；
3. 指出 `cannot-tell` 那两行是**什么都没声明**（沉默不等于通过），这与「不兼容」是两件事；
4. 指出四桶里 `improved` 为 0 的含义：今天能跑、新版本会挂的单元，在这台机器上**一个也没有**。

## 不可以说

- 「升级会修好」「装了就没事」「官方是有意的不兼容」——都不在证据里；
- 不评价官方灰度策略（跟帖里那句话不是我们能核的）；
- 不承诺修复时间、不催维护者；
- 不把这台机器的 130 个单元说成「你的机器」。

## 边界句（必须原样进正文）

> 以上判的是**声明层**：只看「声明区间 vs 目标运行时」，没有任何一个单元在 `0.2.2-rc.1` 上真正启动过；
> 而且这是**一台机器、一个 profile** 的读数，换台机器就不成立。
