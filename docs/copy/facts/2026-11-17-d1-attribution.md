## 真实案例（不是数字，是时间线）

`jjjjjjjjnnjnn/dsh-triage` 的 **issue #1**（作者 `CyrusCCSY`，开于 `2026-11-08T01:44:27Z`，**至今 open**）：

- 现象：`@deepseek-ai/dsh-base` / `dsh-web-app` 被报成 **“not installed under the profile”**，而宿主实际加载正常。
- 用户贴出的那两行 `roots` 就是入口：诊断只报它**搜过哪两处目录**，没有说「这个包在第三处（内核）里」。
- 我方修复在 `0.3.5` / `0.3.6`（内核自带 bundle 不再被判「未安装」；另一处会造成误报的判定收窄），
  `2026-11-17T13:19:58Z` 已在该 issue 里跟进 `0.3.11`。**对方至今未回。**
- **这条案例的用处**：它证明「拒绝 / 未安装」之后的**归因**是可复现的缺口，而不是一个理论上的建议。
  **它不是**「上游有 bug」的证据——误报发生在我们这一侧。

## 可以说什么

- 拒绝的**语义**是对的：我们复算的 27 条金标与上游没有一条分歧；问题在**拒绝之后的那句话**。
- 用户现在拿到的是「denied / 装不上 / 行被禁用」，拿不到三件事：
  **① 实际解析到的是哪一份副本**（realpath / 哪个 manifest）；**② 这一份是被谁带进来的**（bundler / profile / 共享缓存）；
  **③ 具体哪一条约束没被满足**（哪个包、哪条区间、目标版本是什么）。
- 最小改法是**只加输出、不改判定**：在既有拒绝结果上补这三个字段即可，不引入新的语义，
  也不改变任何 `admitted` / `denied` 的结论。
- 845 / 345 / 242 说明这不是个例：故障帖里有七成没人回，用户只能自己贴日志问人。
- 我们自己踩过的坑可以公开：行级归因要读三处（profile manifest、实际解析位置、嵌套副本），
  并且必须区分「没装上」与「装的是本地路径 / 内核自带」——**「profile 磁盘上没有」不等于「没有」**。

## 不可以说

- **不能说「上游错了」**：27 条金标零分歧；这是能力缺口，不是缺陷。
- **不能把这个 issue 写成「建议你们采用我们的工具」**：正文不出现安装命令、不出现包名以外的自荐。
- 不能给「多少比例的用户会遇到」这类比例：样本是 845 条讨论与 1545 条 Q&A，不是普查。
- 不能把声明层结论说成运行期保证（`admitted` ≠ 跑得对；`unconstrained` ≠ 能用）。
- 不能提任何我们没测过的平台 / 版本组合（本机只测 Windows + 单 pnpm 版本 + Node 24）。
- 不能把这次贡献和 D5 绑在一起卖惨：正文不出现 D5、不出现「我们没人用」。
