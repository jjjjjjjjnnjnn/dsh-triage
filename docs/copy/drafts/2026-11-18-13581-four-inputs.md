That is a fair correction, and I think you have found the input my model was missing.

Composition is not driven by `dsh.profile.bundles` alone. The profile boot stacks patch layers in this order: each bundle in `dsh.profile.bundles`, then **the profile's own `cordis.patch.yml`** (the user layer, hot-reloaded), then any `--patch` overlays. A row in `cordis.patch.yml` can name a package directly, so a plugin can be composed without its name ever appearing in `bundles`.

So the facts that decide "does it load" are four, not three:

1. a row names it in the patch layer
2. the bundle is selected in `dsh.profile.bundles`
3. the package resolves (`node_modules`, the shared layer, or the kernel)
4. the compatibility guard accepts its declared requirements — unmet ones disable the row (`Plugin <name>@<ver> is incompatible with dsh <runtime> …`) unless an exact-version exemption was granted with `dsh plugin allow-version`

Your linked build passed 1+3+4 and skipped 2, which is exactly why it worked. "Not in `bundles`" is not an error state by itself; it becomes one only when the patch row is also gone.

That narrows what I wrote in #13609, and I will post the correction there rather than leave a claim that your machine already refutes.

For a complete uninstall check, the decisive file is `<profile>/cordis.patch.yml`: if a row still names the package, removing the dependency takes away the code but not the intent to load it.

Boundary: this reads published manifests and the upstream source, not your machine; declaration-layer admission does not prove runtime health.
