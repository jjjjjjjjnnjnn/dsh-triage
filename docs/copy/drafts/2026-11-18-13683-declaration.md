One addition for anyone who will rely on the declaration rather than this report.

I recomputed `dsh-move-up@0.4.5`'s `engines.dsh` (`>=0.2.1-rc.5`) against the three hosts you tested: all three are admitted, so the report and the declaration agree. But the same range also admits `0.3.0-rc.1` and `1.0.0` — a lower bound with no upper bound means the gate will keep admitting every future major, including one that removes the structured menu API your DOM fallback exists for.

That is not a defect in your report; it is the boundary of what a declaration can promise. Your protection against that future is the runtime capability check plus the DOM fallback, which are runtime properties. It is worth saying so explicitly, because "pass on 0.2.2-rc.3" and "will pass on 0.3" are different claims and only the first one has been measured.

The second thing worth writing down: all three host packages are `optional` peers. That is what makes the sandboxed install work (no `@deepseek-ai/cordis` from the registry, no `ENOTCACHED`), and it is also why the admission gate cannot see a missing host — the failure moves to call time, where your own readable error covers it. Both sides of that trade are deliberate; the cost is that no gate will warn a user who ends up without the host package.

Anyone can check the range themselves:

```bash
npm view dsh-move-up@0.4.5 engines peerDependencies peerDependenciesMeta --json
```

Boundary: this reads published manifests and the upstream source, not your machine; declaration-layer admission does not prove runtime health.
