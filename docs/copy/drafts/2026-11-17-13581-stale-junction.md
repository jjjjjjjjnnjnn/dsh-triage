One consequence worth adding to the report: the stale junction does not only block the reinstall, it also keeps the *uninstalled* plugin resolvable.

`pnpm remove` (or the plugin page's uninstall) removes the dependency entry and, if the app is well behaved, the name from `dsh.profile.bundles`. But `node_modules/<name>` is a separate fact. While that junction still points at a directory that exists, anything resolving by package name from the profile can still find it — so you can end up with a plugin that is "uninstalled" and still reachable. That is the mirror image of #13609: there, installed but not selected; here, unselected but still resolvable.

Two states of the leftover matter, and they fail differently:

```powershell
$p = "$env:DSH_HOME\profiles\desktop\node_modules\dsh-sensenova-pool"
(Get-Item $p -Force).LinkType, (Get-Item $p -Force).Target
Test-Path (Get-Item $p -Force).Target      # False => dangling
```

- **Target still exists** → the copy resolves; expect a ghost plugin (it may load even though nothing selected it).
- **Target gone** → the copy is dangling; expect resolution errors that read like "missing package" even though every manifest looks right.

So after the repair, two checks rather than one: the junction is gone **and** the name is out of `dsh.profile.bundles`:

```powershell
node -e "const p=require('./package.json');console.log(p.dependencies?.['dsh-sensenova-pool'], p.dsh?.profile?.bundles)"
```

On your point 3 ("surface pnpm's stderr"): agreed, and the `[ERR_PNPM_EPERM]` line is already the best sentence in the whole report — it names the path, the temp directory and the operation, which is more than `operation-error` will ever tell anyone.

The `rmdir` vs `Remove-Item -Recurse` warning is the most valuable line in your post; please keep it near the top if you file this as a bug.

Boundary: this reads manifests and local files, not your machine; declaration-layer admission does not prove runtime health.
