# 升级前先问一句：`upgrade --to` 会摘掉我哪些插件？

> 状态：**未发布**（草稿，R45）。数字来自 `data/results/upgrade-*.json` 与 `upgrade-declarations-*.json`，文末给复算命令。
> 这一篇比前两篇更重要：它写的是**我们自己的结论边界**。

## 起因

DSH 的 rc 版本发得很勤。每次升级前，用户其实都有一个具体问题：

> 我这一堆插件，升上去之后哪些会被 loader 摘掉？

这件事**不需要装、不需要起服务**就能回答：把 admission 的运行时换成目标版本，逐行判一次。

```sh
dsh-triage upgrade --to 0.2.1-rc.4
```

它给四个桶，**恰好落一个**：

| 桶 | 含义 |
|---|---|
| `would-be-denied` | 目标运行时会拒这一行/这个 bundle（附「今天是不是已经被拒」） |
| `cannot-tell` | 声明沉默（没写任何 DSH 声明）或包根本没装——**沉默不等于通过** |
| `improved` | 今天被拒、目标放行 |
| `likely-fine` | 目标放行，且今天不是被拒状态（名字就叫「像没事」，不叫「没事」） |

真机跑一份 192 单元的 profile（0.2.1-rc.4 → 0.3.0）：**119 拒 / 73 不可判 / 0 改善 / 0 旧账**，同一批行换成「目标=当前」则是 **0 拒**（对照组）。
产物：`data/results/upgrade-2026-10-30T03-40-00.000Z.json`。

## 「改善」这个桶，我们一开始以为能轻松点亮

逻辑上 `improved` 很简单：一条声明**今天拒、目标放行**。设计时我们以为只要在测试组合里放一条声明 `>=0.2.1-rc.6` 的行就行。

真去扫了一遍 registry 之后，结论变了。扫 1584 个带 `dsh-plugin` / `deepseek-harness` 关键词的包：

| 分类 | 数量 |
|---|---|
| 在 `0.2.1-rc.4` 上被拒 | **202** |
| 其中「今天拒、**更新的**目标放行」（前向） | **0** |
| 只在**更旧**的目标放行（降级几何） | 113 |
| 任何目标都不放行（区间写死在别处） | 89 |

产物：`data/results/upgrade-declarations-2026-10-29T07-05-00.000Z.json`（网络快照，重跑数字会变）。

**前向是 0**，原因很朴素：npm 上 `next` 就是我们正在跑的那个 rc.4，没有"更晚的版本"可写；而作者们写区间时只会写已经存在的版本。

所以我们真正的见证是**降级几何**：`dsh-noname-kit@1.10.8`、`dsh-motion-ui@0.8.8`、`@kirkchinese/dsh-citeciter@0.9.0-beta.6` 这三个真实包，在 `0.2.1-rc.4` 上被拒、在 `0.2.1-rc.3` 上放行。跑 `--to 0.2.1-rc.3` 时它们落 `improved`，同时另外三行分别落另外三个桶（四桶全非空）。
产物：`data/results/upgrade-mixed-2026-10-29T07-10-00.000Z.json`。

**对外口径因此改了**：`improved` 有真机证据，但只有"回到插件钉的那个版本"这一种形状；「升级会修好它」这句话在今天的生态里**没有样本**（我们把它记成 `BS-42`，写得越清楚越好）。

## 顺带发现的一个区间陷阱

判断用的是 `semver.satisfies(version, range, { includePrerelease: true })`。于是：

| 作者写的区间 | 放行 `0.2.1-rc.4`？ | 为什么 |
|---|---|---|
| `>=0.2.0-rc.1 <0.3.0-0` | ✅ | 有 rc 下限，`includePrerelease` 让同一行的后续 prerelease 通过 |
| `^0.2.0-rc.1` | ✅ | 同上 |
| `^0.2.1` | ❌ | `0.2.1-rc.4 < 0.2.1` |
| `0.2.1-rc.3`（精确钉） | ❌ | 精确钉只放行那一个版本 |

这就是为什么你会看到不少插件写成 `>=0.2.0-rc.2 <0.2.1-0 || >=0.2.1-rc.1 <0.3.0-0` 这种两条并集——它们是在绕 prerelease 的排序，不是随手写的。

**给你的建议**：写 `>=0.2.0-rc.1 <0.3.0-0` 这类「带 rc 下限 + 有上界」的区间，别精确钉当前 rc。精确钉会让你下一次 rc 就掉线，而且是**静默**掉线（见第一篇）。

## registry 只是注解，不能改结论

`upgrade --registry` 会去查「有没有一个已发布版本，它的声明承认目标运行时」。这件事**只做注解**：

- 真联网跑一次：`facts = 2` / `failures = 0`，两个注解都挂上了（都 `admits_target: false`）；
- 而每个单元的桶与计数**一字未变**。

产物：`data/results/upgrade-registry-live-2026-10-29T07-15-00.000Z.json`。

为什么不让它改结论：registry 回答的是「作者发布过什么」，不是「你这台机器上的这一行会不会被准入」。把「有个更宽松的版本可以换」写成「升级会修好」，就是把两件事混成一件。

## 怎么自己复核

```sh
# 1) 你这台机器上：换目标版本看影响（默认离线、只读）
dsh-triage upgrade --to <目标版本> --json

# 2) 生态形状（网络快照）
node scripts/scan_upgrade_declarations.mjs --stamp <ISO> --pages 3

# 3) 策展组合上的四桶（本仓沙盒，不碰你的 ~/.dsh）
node scripts/prepare_upgrade_mixed_profile.mjs
node scripts/record_upgrade_impact.mjs --stamp <ISO> --to 0.2.1-rc.3 \
  --dsh-home sandbox/upgrade-mixed/home --profile mixed --expect-improved
```

## 诚实边界（这一节比上面都重要）

- **声明层，不是行为层**：`would-be-denied` 说「按声明不会被准入」，不说「插件坏了」；`likely-fine` 说「声明上像没事」，不说「功能可用」。
- **目标版本不一定存在**：默认离线，`--to 0.3.0` 是合法的**假设输入**；它的存在性没被验证。
- **只判已装的**：没装的插件没有行、没有答案。
- **一份 profile 一个答案**：换 profile、换 home、换 OS/arch 都不保证一致。
- **策展组合不是随机样本**：四桶见证用的是我们挑的 6 个真实包，声明没改，但选谁是我们决定的。
