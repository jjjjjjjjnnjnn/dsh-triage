# 草稿 04 · 中文长文：rc 升一格，你的「已装集合」为什么会被大面积拒

> 目标读者：装过几个 dsh 插件、遇到过「升了个小版本，工具不见了」的人。
> 全文只用真机产物：`data/results/upgrade-card-2026-10-31T09-00-00.000Z.json`（卡片）与
> `data/results/market-baseline-2026-10-31T06-40-00.000Z.json`（生态现状）。

---

## 一、现象

上游 `0.2.1-rc.5` 发布那天，我做了一件很朴素的事：把一份**钉在 rc.4** 的 profile，拿去问「升到 rc.5 会怎样」。

结果不是「可能有点小问题」，而是一张表：

```
192 个单元（2 bundle + 190 行）
  119  升上去会被拒
   73  判不了
    0  会变好
    0  像没事
```

我当时的第一反应是「工具写错了」。第二反应是去看原因行——一百多条原因几乎一模一样：

```
peer @deepseek-ai/dsh-shell-env@0.2.1-rc.4 不含 0.2.1-rc.5
```

## 二、为什么会这样

因为**声明是精确钉版本的**。上游那一批包把 peer 钉在 `@x@0.2.1-rc.4`，而不是一个区间。只要目标运行时变一格，
所有声明都落在区间外，admission 就按规则把它们拒掉——这不是 bug，是声明的形状决定的。

这件事有个很容易搞混的地方，值得单独说：

- **「会被拒」不等于「升级会坏」**。这是**声明层**的判断：只看「声明区间 vs 目标运行时」。运行期会不会真的挂，
  这张表不回答。
- 反过来，这张表也**不许**说「升级会修好」。`improved` 那一桶今天是 0，明说了「今天被拒、目标放行」一个都没有。

## 三、你可以自己查（全程离线）

```console
$ dsh-triage upgrade --to 0.2.1-rc.5 --card     # 人看的卡片
$ dsh-triage upgrade --to 0.2.1-rc.5 --json     # 同一条判定，机器可读
```

`--to` 给**精确版本**时不联网；只有 `next` / `latest` 这两个词会去读一次 npm 的 `dist-tags`，而且解析出来的版本
必须与 registry 逐字相同才会被用（`v0.2.1-rc.5` 会被拒，而不是被悄悄改写成 `0.2.1-rc.5`）。

真正有意义的是**你自己的组合**：同一张表在我的沙盒里是 119，在你的机器上应该不一样——不一样才对。

## 四、如果你是插件作者

两条低成本的做法：

1. 声明用区间（或至少 `engines.dsh`），不要让 peer 钉死在一个 rc 上；
2. 0.2.x 支持 profile 级的**精确版本对豁免**（`compatibility.json`），卡片里的修复建议就是它。

## 五、为什么做这个工具、以及它不做什么

生态现状（同一天的采集）：诊断类目整周 **3,074** 次下载，市场类是 **513,534**，装饰类是 **552,956**；上游最近
**854** 条讨论里 **405** 条是故障帖、其中 **256** 条零回复。也就是说：**痛是真的，回答的人很少**。

它只做三件事：行级归因（我的工具为什么不见了）、组合判断（候选 × 我已装的会不会撞）、升级影响（升上去会掉什么）。
它**不做**：插件市场、启动器、装/卸/回滚、通用安全扫描，也不做全网兼容矩阵。没证据的时候它说 `unknown`，
不会给一个看起来很像结论的分数。

MIT、公开、只读、默认不联网（你让它查 registry 才查）。
