# 草稿 04 · 技术解析：DSH 小版本升级后，为什么已装插件会“静默消失”？

> 目标读者：使用或开发 DSH 插件、经历过“升级一个小版本后部分功能失效/消失”的开发者。
> 文中实测数据均来自仓内可复算产物：`data/results/upgrade-card-2026-10-31T09-00-00.000Z.json` 与 `data/results/market-baseline-2026-10-31T06-40-00.000Z.json`。

---

## 一、现象：没有报错，但插件功能不见了

不少使用 DSH 的同学在升级版本时，都踩过类似的坑：原本工作正常的 hooks、MCP 工具或扩展面板，在把 DSH 升级到新版本（例如 `0.2.1-rc.5`）并重启后，突然无法使用。

更令人困惑的是，界面上往往没有任何显眼的红字报错或崩溃弹窗。上游确实会在启动日志里报告那次准入拒绝，但那只是滚动日志里的一行，重启之后就翻不到了——留下的印象只有「东西没了」。

许多人直觉会以为是插件运行时代码发生了致命错误导致崩溃，但实际上，这些插件甚至**根本没有进入运行加载阶段**。

## 二、机制剖析：什么是 DSH 的 Admission（准入）？

DSH 的 Loader 在启动组装 profile 时，会对配置中的每一项进行声明层求值，即 **Admission（准入）** 检查。

理解这个机制的关键在于两点：

1. **求值粒度在“行（Row）”而非“包（Bundle）”**：一个插件包在顶层声明可能看似符合规范，但其内部在 profile 注册的某个具体 entry 行，如果声明区间不满足要求，就会被准入机制单独拦截并摘除；
2. **社区常见的精确版本锁定**：许多插件在打包发布时，为了稳妥，在 `package.json` 的 `peerDependencies` 中指定了精确的依赖版本，例如：
   ```json
   "peerDependencies": {
     "@deepseek-ai/dsh-shell-env": "0.2.1-rc.4"
   }
   ```
   这就埋下了隐患：当宿主升级到 `0.2.1-rc.5` 时，由于精确版本号不匹配，准入求值立即判定该行不满足运行要求。Loader 为了防止不可控的运行时崩溃，直接在启动阶段静默剔除了该行（`phase=no-fiber`, `disabled=true`）。

对用户而言，表象就是：安装仍在，但界面功能“凭空消失”。

## 三、真实数据：192 个单元在 rc.5 上的准入表现

为了量化这一现象的影响面，我们基于一套典型的沙盒配置（包含 2 个 bundle 与 190 个 loader entry 行，共 192 个单元），对照目标版本 `0.2.1-rc.5` 进行了全面的准入推演。

测试产出的四桶统计数据非常典型（详见 `data/results/upgrade-card-2026-10-31T09-00-00.000Z.json`）：

```text
192 个单元（2 bundle + 190 行）
  119  会被准入拦截 (would-be-denied)
   73  声明不足无法判定 (cannot-tell)
    0  升级后变好 (improved)
    0  确定无影响 (likely-fine)
```

查看那 119 条被拦截的详细原因，绝大多数完全一致：

```text
peer @deepseek-ai/dsh-shell-env@0.2.1-rc.4 不含 0.2.1-rc.5
```

根据上游社区 Discussions 的近期数据采样（`data/results/market-baseline-2026-10-31T06-40-00.000Z.json`），在 854 条讨论中，有 405 条涉及故障排查，其中 256 条未得到解答。可见版本迭代中的静默准入断层是很多开发者频繁遇到的高频痛点。

## 四、本地一键预检与排查方案（dsh-triage）

为了让大家在升级前就能看清“我这套已装插件升上去会掉什么”，我们开发了开源诊断工具 `dsh-triage`。

### 1. 升级前预检

无需真正执行升级，在终端中指定目标版本，即可在本地秒级输出四桶兼容性卡片：

```console
# 输出人类可读的结构化卡片（指定精确版本号时全程纯本地离线计算）
$ dsh-triage upgrade --to 0.2.1-rc.5 --card

# 机器可读的 JSON 格式
$ dsh-triage upgrade --to 0.2.1-rc.5 --json
```

注：当 `--to` 接收精确版本号时完全不依赖网络；只有传入 `next` 或 `latest` 时，才会按需读取一次 npm registry 的 `dist-tags`。

### 2. 当前环境排查

如果升级后已经遇到插件消失，可以使用以下命令定位：

```console
$ dsh-triage audit            # 快速查看当前环境中所有插件行的准入状态与 phase
$ dsh-triage why "[模块或行 ID]" # 精确定位特定插件行被准入拦截的具体根因
```

## 五、对插件作者与用户的建议

针对这一机制，建议在日常开发中注意以下两点：

1. **对于插件作者**：在声明对 DSH 核心包或环境包的依赖时，优先使用合理的 SemVer 范围（如 `^0.2.1`）或配置 `engines.dsh`，尽量避免将 `peerDependencies` 硬编码为单一的 rc 版本；
2. **对于终端用户**：若遇到确实兼容但因声明过窄被拦截的插件，DSH 0.2.x 提供了 profile 级的精确版本豁免能力（`compatibility.json` 或 `dsh plugin allow-version`），可以在本地显式授予豁免，无需等待作者发版。

## 六、总结

`dsh-triage` 坚持纯本地只读分析，不修改用户配置，无隐私收集，旨在提供一个透明、确定的环境分诊层。
